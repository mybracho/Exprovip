# AGENTS.md

## Назначение

Этот репозиторий содержит проект на платформе 1С:Предприятие.

Конфигурация самописная, но использует БСП, поэтому при изменениях нужно учитывать типовые подходы БСП и не ломать механизмы подсистем, общих модулей, ролей, форм, команд и регламентных процедур.

Основная задача агента — помогать с анализом, рефакторингом, исправлением ошибок, написанием 1С-кода, тестов и технической документации. Все изменения должны быть аккуратными, минимальными и проверяемыми.

---

## Язык и стек

Основной язык разработки:

- 1С:Предприятие / BSL;
- управляемые формы;
- XML-файлы метаданных, форм, команд, ролей и прочих объектов конфигурации;
- Проект разрабатывается на EDT

Проект может содержать:

- модули объектов;
- модули менеджеров;
- модули форм;
- общие модули;
- обработки и отчёты;
- XML-описания метаданных;
- файлы форм;

## Общие правила работы

1. Перед изменениями всегда изучай существующую структуру проекта и стиль кода.
2. Не делай массовые изменения без явной необходимости.
3. Не переименовывай объекты метаданных, реквизиты, табличные части, команды, формы, роли, подсистемы и общие модули без отдельного согласования.
4. Не меняй UUID, идентификаторы объектов метаданных и внутренние ссылки XML без крайней необходимости.
5. Не меняй формат обмена, структуру XML/JSON/API, имена полей и типы данных без отдельного указания.
6. Не удаляй код, если не уверен, что он не используется. Сначала найди все ссылки и точки вызова.
7. Не меняй поведение пользовательского интерфейса без явного задания.
8. Не меняй настройки прав, ролей и RLS без отдельного задания.
9. Не меняй код БСП, если это явно типовой механизм БСП. Предпочитай расширение/обёртку/вызов штатного API.
10. После изменений обязательно кратко опиши:
    - какие файлы изменены;
    - что именно изменено;
    - почему это безопасно;
    - какие проверки нужно выполнить.

## Правила для 1С-кода

### Стиль

1. Пиши код в стиле, уже принятом в проекте.
2. Используй русские имена процедур, функций и переменных, если проект уже использует русский стиль.
3. Имена должны отражать смысл, а не техническую деталь.
4. Избегай слишком общих имён:
    - `Результат`;
    - `Структура`;
    - `Таблица`;
    - `Флаг`;
    - `Данные`.

   Используй более точные имена:
    - `ЗапросВыполненУспешно`;
    - `ДанныеФайлаОбмена`;
    - `ТаблицаСтрокДокумента`;
    - `ПараметрыОтбора`;
    - `РезультатЗаписиФайла`.

5. Не используй транслит в новых именах.
6. Не смешивай русский и английский в одном имени без необходимости.
7. Комментарии пиши на русском языке.
8. Комментарии должны объяснять причину решения, а не пересказывать код.

### Процедуры и функции

1. Функция должна возвращать значение. Процедура должна выполнять действие.
2. Если метод называется как действие, чаще всего это процедура:
    - `ВыгрузитьЗапросКотировок`;
    - `ЗаписатьФайлОбмена`;
    - `ОтправитьЗапросВAPI`.

3. Если метод отвечает на вопрос или формирует значение, чаще всего это функция:
    - `СформироватьИмяФайлаОбмена`;
    - `ПолучитьПараметрыОбмена`;
    - `ПодготовитьXMLЗапроса`;
    - `ЗапросКотировокЗаполненКорректно`.

4. Не создавай универсальные процедуры с большим количеством флагов.
5. Предпочитай маленькие методы с понятной ответственностью.
6. Если метод стал слишком большим, предложи декомпозицию.

### Ошибки и исключения

1. Не подавляй исключения без обработки.
2. Если используется `Попытка ... Исключение`, обязательно сохраняй или выводи полезную информацию об ошибке.
3. Для технических ошибок формируй понятное сообщение:
    - где произошла ошибка;
    - с каким объектом;
    - какой вариант обмена/операции выполнялся;
    - текст исключения.

4. Не показывай пользователю лишние технические детали, если ошибка должна быть пользовательской.
5. Не используй пустые блоки `Исключение`.

### Запросы

1. Проверяй, что запрос не меняет логику отбора.
2. Если меняешь запрос, объясни изменение словами.
3. Следи за ситуациями, когда соединение превращается в фильтр и отбрасывает строки.
4. Для табличных частей с флагом `Выбран` учитывай логику:
    - если отмеченные строки есть — фильтровать по ним;
    - если отмеченных строк нет — не применять фильтр.
5. Не усложняй запрос временными таблицами без необходимости.
6. Не меняй имена полей результата запроса без согласования, если они используются дальше в коде.

### Клиент-сервер

1. Соблюдай разделение клиентского и серверного кода.
2. Не вызывай серверные методы с клиента без необходимости.
3. Не передавай на клиент тяжёлые объекты, если достаточно структуры, массива или таблицы значений.
4. Для получения отдельных реквизитов ссылочного объекта используй `ОбщегоНазначения.ЗначенияРеквизитовОбъекта`. Не получай объект через `ПолучитьОбъект()`, если не требуются его табличные части или методы объекта.
5. Не выполняй тяжёлые запросы на клиенте.
6. Учитывай директивы компиляции:
    - `&НаКлиенте`;
    - `&НаСервере`;
    - `&НаСервереБезКонтекста`;
    - `&НаКлиентеНаСервереБезКонтекста`.

## Правила для XML-файлов метаданных и форм

Codex может править XML-файлы метаданных и форм, но такие изменения считаются повышенно рискованными.

### Разрешено

1. Исправлять очевидные текстовые значения:
    - синонимы;
    - заголовки;
    - подсказки;
    - комментарии;
    - представления;
    - настройки видимости, если задача явно об этом.

2. Добавлять или корректировать элементы формы, если структура понятна и изменение локальное.
3. Исправлять привязки к уже существующим реквизитам формы, если связь очевидна.
4. Менять порядок элементов формы только по явному заданию.
5. Исправлять XML только после изучения соседних аналогичных элементов.

### Запрещено без отдельного согласования

1. Менять UUID/ID объектов метаданных.
2. Менять внутренние идентификаторы элементов формы, если непонятно, где они используются.
3. Массово форматировать XML-файлы.
4. Пересоздавать XML-файл целиком.
5. Удалять элементы формы.
6. Удалять реквизиты, команды, группы и декорации.
7. Менять типы реквизитов.
8. Менять владельцев, пути, ссылки на команды и обработчики событий.
9. Менять настройки ролей, прав и ограничений доступа.
10. Менять состав подсистем.

### Обязательное правило

Если изменение XML формы можно сделать через EDT/Конфигуратор безопаснее, сначала предложи такой вариант.  
Если всё же правишь XML напрямую, изменение должно быть минимальным и легко проверяемым через `git diff`.

## Правила для БСП

1. Учитывай, что проект основан на БСП.
2. Перед изменением общих механизмов проверь, не является ли код частью БСП.
3. Не изменяй типовые общие модули БСП без явного указания.
4. Предпочитай использовать штатные методы БСП:
    - `ОбщегоНазначения`;
    - `ОбщегоНазначенияКлиент`;
    - `ОбщегоНазначенияСервер`;
    - `РаботаСФайлами`;
    - `УправлениеСвойствами`;
    - `ДополнительныеОтчетыИОбработки`;
    - другие подсистемы БСП, если они уже используются в проекте.

5. Если предлагаешь изменение, которое затрагивает БСП, отдельно укажи риск.

---

## Работа с обменами, XML, JSON и API

1. Не меняй публичный формат обмена без явного указания.
2. Не переименовывай поля XML/JSON/API без согласования.
3. Сохраняй обратную совместимость, если не сказано обратное.
4. Для дат и времени явно учитывай формат:
    - наличие или отсутствие часового пояса;
    - локальное время;
    - UTC;
    - формат ISO 8601.

5. Для денежных значений не используй строковые операции без необходимости.
6. Для XML учитывай экранирование спецсимволов.
7. Для API-обмена разделяй:
    - подготовку данных;
    - сериализацию;
    - отправку;
    - обработку ответа;
    - логирование;
    - обработку ошибок.

## Работа с табличными документами и таблицами значений

При работе с табличными документами:

- разделяй подготовку данных и вывод данных;
- не смешивай бизнес-логику с оформлением макета;
- используй области макета с понятными именами;
- не дублируй вывод строк без необходимости.

При работе с таблицами значений:

- явно задавай структуру колонок;
- используй понятные имена колонок;
- не полагайся на порядок колонок, если можно обращаться по имени;
- при необходимости используй `Свернуть`, `НайтиСтроки`, `Скопировать`, `Выгрузить` осознанно.

При создании структур:

- не создавай структуру через строку ключей и список значений в конструкторе;
- создавай пустую структуру через `Новый Структура`, а затем добавляй поля через `Вставить`;
- для каждого поля задавай значение по умолчанию подходящего типа.

Пример:

```bsl
Результат = Новый Структура;
Результат.Вставить("Номенклатура", Справочники.Номенклатура.ПустаяСсылка());
Результат.Вставить("КоличествоЗаказа", 0);
Результат.Вставить("НомерСтрокиЗаголовков", 0);
```

## Работа с Git

1. Перед изменениями проверь статус:

```bash
git status
```

2. Не работай поверх чужих незакоммиченных изменений без предупреждения.
3. После изменений покажи краткое резюме diff.
4. Не делай commit без явной команды пользователя.
5. Не делай push без явной команды пользователя.
6. Не меняй `.gitignore`, настройки CI/CD и служебные файлы без необходимости.

## Что делать при неуверенности

Если есть риск сломать метаданные, форму, права, обмен или БСП-механизм:

1. Не вноси изменение сразу.
2. Сначала покажи план.
3. Укажи файлы, которые нужно изменить.
4. Объясни риск.
5. Дождись подтверждения.

## Особые предпочтения проекта

1. Основной язык общения и комментариев — русский.
2. Предпочтительны понятные имена на русском языке.
3. Код должен быть максимально практичным и поддерживаемым.
4. Важна совместимость с 1С и БСП.
5. Важна проверяемость изменений через Git.
6. Для форм и XML-метаданных изменения должны быть особенно осторожными.
